# Luxembourg bus demand explorer

From the repository root, run `python3 -m http.server 8000` and open `http://localhost:8000/interactive_visualizer/`. The page loads `data/reqreate/area_550/550_raw_requests.json` and `550_pois.json` automatically. If you open `index.html` directly, choose both files with the file buttons. The request input is REQreate's raw JSON object with `"num_data:"` and ID-keyed `"requests"`. Each request supplies `reqid`, `is_prebooked` (1 or 0), `origin` and `destination` as `[latitude, longitude]`, `earliest_departure`, `latest_arrival`, `time_stamp`, `lead_time`, `direct_distance`, and `direct_travel_time`. Times are seconds on the service-day axis; distances are metres. The node IDs identify locations in request details. The metadata sidecar is not needed.

Filter by booking type and earliest departure, select a request or enter its ID for details, and turn on aggregated origin–destination flows. Circles count visible origins and destinations at each coordinate. The list shows the earliest 200 visible requests; the ID field reaches any request. All 8,000 requests contribute to the map and counters. The POI layer shows all 540 records, including the 270 marked not walkable. Colors group POIs by their primary OSM tag; a selected point shows every tag and its walkability. The color groups count each POI once. Expand **All POI types** for the full list of OSM tag values and counts; a POI with multiple tags appears in multiple type counts.

Open `scenario.html` for the Julia scenario viewer described below. It accepts a file such as `../data/instances/550_base.json`.

Use the route, booking type, and desired pickup time controls to filter demand. Circle size represents boardings plus alightings at each logical stop. Turn on origin–destination flows to see each request's straight line between its two stops. Select a stop or a request for details; drag and scroll the map to move and zoom.

To view road distances, choose the matching `data/distance_matrix_550.json`, then click **Show road distances**. The labels show directed road distances between consecutive stops in the selected route and direction. In **All routes**, a shared segment is labeled once; choose a direction to see its exact value. Selecting a request also shows its origin-to-destination road distance. Click **Hide road distances** to remove the labels. The labels come from the matrix's road routing estimates; the map still connects stops with straight lines.

The **Generator checks** section audits the loaded instance for request counts and IDs, per-pattern allocations, forward stop order, pickup windows, service-period bounds, and booking leads. Click an issue to inspect its request or candidate on the map; **Show flagged requests only** filters the map and request list. Selecting a request shows its lead time and matrix travel time.

Turn on **Debug mode: rejected candidates** and choose `data/debug/rejected_candidates_550.debug.json` to inspect rejected raw preferences and any rejected booking assignments. Dashed map lines connect their stops; blue means pickup before the feasible bound, red means after it, and purple marks a booking rejection. The list is sorted by minutes outside the feasible pickup bounds. Select a line or list item to see its reasons, desired and booked times, feasible bounds, operating hours, and source stops. Filter by rejection reason, route and direction, booking type (for assigned candidates), or whether pickup is outside its bounds. The demand time slider does not hide debug records outside service hours. Debug checks flag mismatched counts, seed or service date, stop order and mapping, pickup windows, operating hours, and rejection reasons.

For a deeper check, choose the matching `data/candidate_pool_*.json`. With the current raw-pool format, the viewer checks candidate stop order, source-stop mapping, pickup windows, and service bounds. It matches each instance request against the pool by route, stops, and desired time; a repeated match is left ambiguous because the instance does not store candidate IDs. Older pool files with booking and trip provenance retain their more detailed lead, travel-time, and timetable checks. Choose `data/timetable_*.json` to compare service dates; detailed source-trip comparisons require the older pool format. All files stay local. Without a candidate pool, lead checks use the current generator defaults (pre-booked: 1–3 whole days; dynamic: 5–30 minutes).

Run `node interactive_visualizer/check_reqreate.js` to check the REQreate viewer, or `node interactive_visualizer/check.js` to check the scenario viewer against the included low/base/high scenarios, debug records, and injected generator faults.

Leaflet and OpenStreetMap map tiles load from the internet. The JSON file remains local. The scenario viewer accepts schema-version-2 instance JSONs produced by `src/reqreate_gen/generate.jl` (including multi-line networks).
